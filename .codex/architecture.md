# architecture

## Current Summary

- `czjLLM/prompt_pipeline/pipeline_controller.py` remains the compatibility/orchestration facade; focused runtime helpers live under `prompt_pipeline/runtime_support/`, while existing imports are preserved through re-exports.
- SQL/Table/ES producer row/document concurrency and prompt-slice concurrency are separate desired widths. The shared process-local `ExecutionBudget` is the hard leaf-execution ceiling and is intentionally excluded from semantic identity.
- `combine_utils.py` remains the compatibility boundary for Success discovery, output placement, final writes and legacy cleanup; JSON repair/combination and slice-merge logic live in focused modules.
- Row Merger remains downstream writeback coordination and Output Profile remains the final strict validation boundary. Reduction Core does not own either boundary.
- ES connection/pending behavior is separated into adapter, pending-policy and value-helper boundaries. Model metadata persistence uses allowlisted non-secret fields; credentials and raw endpoint URLs are excluded.
- Per-run LLM auditing records authoritative API usage tokens/context metadata plus optional local prompt-component token estimates. Context size is never guessed from a display name; CSV/XLSX artifacts are produced per run. The Windows GUI polls the current run CSV for a default-collapsed distribution view, while numeric-only prompt-component handoff metadata lives outside TODO/RUNNING so it cannot enter the prompt queue.
- Reduction Engine v1 A–L plus the L3 release-audit corrective and documentation closure are present at verified `main` merge `99d79676b16b7fed54f9cf6e701441db79846cea`.
- Reduction flow is map/member execution → reducer → optional hierarchical rounds → final result → optional persisted aggregate/writeback. The core owns strict config, deterministic/semantic/structured-relational reducers, atomic checkpoints, shared execution budget, executable stages, explicit partial success and cooperative cancellation.
- Collection boundaries use immutable ordered `LogicalWorkUnit` / `CollectionManifest` snapshots. SQL/ES adapters build snapshots and idempotent aggregate sinks persist `AggregateOutput` using deterministic lineage identity.
- v1.1 lineage convenience helpers are pure read-only projections/comparisons of the canonical aggregate mapping, validating the existing deterministic aggregate ID; they never serve as a second truth or interfere with sink conflict/freshness policies.
- Persisted SQL/ES destination output is cross-run reuse authority when semantic freshness is explicitly configured. Runtime round workspaces are reconstructable; committed checkpoints are resume authority. A v1.1 evaluation deliberately deferred any second semantic/member result cache until measured duplicate-call evidence exists.
- Composition is bounded, not a generic DAG: one nested ReductionStage level, at most four active PipelineRef names, cycle detection, and no semantic reducer in a nested ReductionStage.
- Production cancellation is cooperative safe-drain. A run-scoped cancel intent stops new scheduling/semantic continuation while consumer/merger/writeback and already-running external calls reach safe boundaries.
- Production observability uses payload-free bounded JSONL, cumulative counters and a separate Reduction Status surface. Operational observer/cancellation state is excluded from semantic fingerprints.
- v1.1 adds one optional Python-only final-result quality/coverage hook at the `ReductionStage` boundary. The hook receives the final payload plus existing safe stage metadata, returns scalar quality metrics/warning codes or an explicit rejection, and contributes its semantic metadata to fingerprints without introducing a scorer registry/YAML platform.
- Retention is disabled by default, ownership/lease/claim based, bounded, symlink/containment guarded, and never adopts legacy unmarked artifacts. After deletion-budget exhaustion, later candidates still undergo validation/classification/counters but no further deletion is attempted.
- Successful hierarchical final writes use `cleanup_transient_on_success: true` by default, which performs the post-success transient cleanup path with effective transient TTL zero. Set it false to retain successful runtime workspaces for `transient_runtime_ttl_hours`.

## Current Processing Quality architecture (accepted through PR #239)

- `czjLLM/utilities/processing_quality.py` emits bounded, run-scoped `processing_quality_events_<run>.jsonl` records adjacent to the existing per-run request CSV. Fixed site/code taxonomy covers Consumer, Row Merger retry, Producer, Stage Runner and leaf Worker; typed SDK subcodes further refine eligible call-site exceptions. These are **catch-site observations**, not unique failed documents, provider-outage proof or an API failure-rate denominator; no document IDs, slice IDs, prompts, raw exceptions or secret endpoints may appear in run-only events.
- `processing_quality_report` uses the existing strict writer/reader/accumulator and supports one stopped run or bounded history, an allowlisted run-incident family projection and read-only archived segment replay. A manual stopped-producer rotation command creates consecutive numbered segments; an opt-in v1 SHA256 manifest detects accidental sealed-archive inconsistencies. This is self-consistency, **not** a signed trust anchor, online rotation or permission to auto-delete.
- The Windows GUI reader replays archived plus active quality JSONL in a background worker, deduplicates accepted event IDs/doc state, uses generation-change invalidation, and fails closed with explicit `capacity_exceeded`/unverified status rather than partial or stale success. Read-side GUI defaults cap event cardinality (50k), retained identity characters (~4m) and single line size (64 KiB). Offline reports retain separate full replay support.
- `processing_quality_disk_spill.DiskBackedQualityAccumulator` is opt-in and uses private temporary SQLite for **exact** event/document identity sets. It preserves `report_version=1`, deletes temporary state on ordinary/error paths, and is **not** a persisted checkpoint or authorization for disk retention/pruning.
- `czjLLM.cli_tools.processing_quality_benchmark` is an opt-in stopped-run comparative child-process benchmark. Per-mode report-only `median_seconds` and parent-clock `median_subprocess_wall_seconds` are distinct; child output is strictly checked for finite numeric data, all sample reports must match full canonical SHA256, and stat-generations of active/archive/manifest must remain unchanged before/after every sample. Linux/macOS OS peak memory uses `ru_maxrss`, Windows uses PSAPI historical `PeakWorkingSetSize`, nullable if unavailable. Windows native measurements and representative workload performance need **operator** verification.
- PR #231 (`a8711e9337b62e4b9c6ad62f37ba3e78ba4e8fea`) is still OPEN/non-mergeable at the compaction baseline; its interrupted-rotation rollback semantics must not be described as shipped.
- Source generation checks are read-only metadata checks, not an atomic filesystem snapshot or a hostile tamper detector. No crash-safe checkpoint, safe online writer/GUI rotation, automated pruning/retirement, independent live ES/LLM acceptance, or full Windows GUI acceptance is established.

## Current ES final-output and persistence integrity

- Strict ES `multidim_event` validation remains at `es_mode/output_profiles/multidim_event.py`: publication `article_date_iso` and `article_date_precision` are validated together (null ↔ unknown, month/year normalization), and linked `event_ids` must refer to unique valid `Event[].event_id` values. `utilities/slice_merge.py` keeps each source date/precision pair atomic rather than recombining halves of different slices or inferring an event date.
- `es_mode/runtime/sinks/es_sink.py` may buffer writes; Row Merger must call `confirm_writeback()` and receive ES bulk acknowledgement before releasing original Success/source artifacts. Failed/unconfirmed attempts preserve replay evidence; ES refresh/search visibility is independently verified, not presumed from enqueue. These are **current design boundaries**, not superseded archive-only records.

## Current single-extract partial resume / smart_reset source identity

- For the **single extract-stage JSON slice merge/writeback** path in `czjLLM/prompt_pipeline/pipeline_controller.py`, `resume` / `smart_reset` must validate the **complete original source** even after some slices have been removed from TODO because Success files exist. The original hash-only manifest at `<item>/_extract_slice_identity/source/original.json` intentionally lives **outside** the resettable `_stage_outputs` directory so smart_reset cannot erase its authoritative source membership evidence.
- Verify original source hash, **ordered** raw slice hashes and original filename mapping, the effective extract stage-task identity, and the dispatched prompt hashes against the saved provenance before keeping existing Success or regenerating transient snapshots. Remaining TODO is never a substitute for the original complete source membership; it can omit previously completed siblings. Any missing, mismatched, stale or ambiguous proof fails closed instead of publishing partial/old combined output.
- Split/retry child prompt files keep their verified parent/child dispatch lineage and must not be mistaken for independent new raw source chunks. Hash-only provenance records do not persist raw input text, prompts, credentials or output values. No extra cache or change to public Row Merger/output schema is introduced.

## Current strict ES importance score normalization

- The `multidim_event` ES output profile permits a **narrow lossless shape correction**: exactly `coverage`, `novelty`, `impact`, `credibility`, `importance_score` may move from article top level into nested `importance`, with `int` (not `bool`) or `null` values. Contradictory nested/top-level scores and unknown keys are rejected, never silently recomputed or overwritten. Generic JSON output processing is unchanged.

## Current cache-aware audit / GUI throughput boundaries

- The append-only per-run LLM audit at `utilities/llm_call_audit.py` writes nullable `cached_input_tokens` and `cached_input_token_source=provider_usage` only for provider-backed cache evidence; missing provider metadata is unknown, not zero. A safe `stage_identity` and local prompt-component token source permit isolation without copying plaintext prompt/task payloads into sidecar handoffs.
- The GUI `job_manager/win_gui.py` reads audit CSV outside the Tk hot path and shows `total_tok_per_s` and `effective_tok_per_s_est` separately from historical `processing_tps`. The first is API input+output divided by positive slice duration; the second subtracts **actual provider cached input** when known, otherwise may use a conservative **heuristic** only after at least two stable template samples within an identical (model, endpoint, task, YAML stage, token-source) group. Neither is pure GPU throughput; estimates never create or overwrite provider usage evidence.

## 2026-10-29 phase 2b claim no-clobber boundary (pending PR)

- At the existing file-backed queue boundary, `pick_and_claim_next_prompts` retains its [(RUNNING_path, item_dir)] API and opt-in `claim_ids_out` mapping. Before moving, basename-count TODO candidates; >1 nested source with one basename defers all to preserve bytes. For unique, reject symlink/path aliases and hardlink sources and use same-device `os.link` exclusive destination publication with file identity checks; unlink source before dispatch/audit. Existing claimed event UUID/Worker linkage remains unchanged. Unsupported hardlink/collision leaves queued item unclaimed. The hardlink + unlink window is not crash-atomic; different RUNNING→TODO/Success paths remain legacy behaviors and must be separately evaluated.

- **No-clobber liveness after producer completion:** before `start_workers`, SQL/Table/ES orchestrator publishes `_producer_done_flag` and `_queue_claim_blocked_event` on `ctx`. Consumer checks empty claim with producer done and no metered or filesystem RUNNING files; remaining TODO raises generic orchestration error and sets blocked event. Coordinator checks that event before the `pending+running==0` gate, then executes normal shutdown and terminal `run_failed(reason=unclaimable_queue_sources)` instead of indefinitely waiting. `stop_event` stays teardown-only, not reused as producer-complete/cancellation signal.

- **Blocked queue teardown:** SQL/Table/ES coordinator sets teardown stop_event after observing producer-complete/blocked signal. Row Merger recognizes ctx._queue_claim_blocked_event jointly with stop_event and performs at most one last merge pass, then exits without requiring registry empty; blocked TODO/Success sources remain untouched for replay. This prevents shutdown() indefinite merger.join(), while coordinator emits terminal run_failed rather than forged completion. Other cancellation/normal-drain modes retain their original registry-empty behavior.

## 2026-10-29 phase 2c — no-clobber queue recovery and Worker Success publication

- Existing `runtime_support.prompt_queue._claim_regular_source_no_clobber` is reused for nested RUNNING→TODO recovery (exclusive hardlink + verified unlink). A recover count and requeue observation exist only after completed move; prior TODO or uncertain aliases leave RUNNING. The TODO→RUNNING picker also refuses existing Success basename, never claiming a new source as an already completed older result.
- `PromptAPIPipeline.proc` publishes nonempty Success from a unique same-directory fsynced staging file via exclusive `os.link`, then runs existing success-identity and RUNNING cleanup. Existing Success is never atomically replaced; collision raises to existing Worker error path without removing queued source. Same-volume hardlink support required. The related queue/memory/model/sink boundaries retain previous semantics. No cross-process transaction, trusted retry family or final sink confirmation is inferred.

- **#254 race semantics:** The initial existing-Success preclaim filter is reinforced with a second check after a successful exclusive TODO→RUNNING move. If an old Worker published while the claim was waiting for RUNNING to clear, restore the new source to its *original* TODO path before claim event/Worker construction. A failed safe restoration yields a payload-free failure, no fabricated work. Success output's staging hardlink cleanup is best effort after atomic publication, so Worker identity/cleanup follows the committed success even when temporary unlink is denied; residual staging is visible but not authoritative output.

- **#254 terminal rollback routing:** An old Success race first attempts exclusive fresh RUNNING→original TODO restoration. Failure raises a typed `QueueClaimRollbackError`, caught around actual streaming picker to set `ctx._queue_claim_blocked_event` and re-raise to consumer incident audit; existing coordinator failure/teardown and blocked Row Merger semantics apply. The exception contains no raw source, model, path or prompt content; it never emits a completed queue claim.

- **#254 producer terminal unblock:** Consumer's typed queue rollback failure sets ctx-shared blocked event. The common pipeline backpressure waiter and SQL/Table/ES `produce_rows` inspect it during row scheduling, deferred-running waits, capacity wait, per-row post-schedule outstanding wait and final drain, preventing the independent producer thread from hanging after Consumer terminates. Producer's progress.prod_done remains false on terminal error; its wrapper sets producer_done_flag in finally as a thread-lifecycle signal only, letting Orchestrator's existing failed shutdown and Row Merger exit proceed without marking queue complete.

- **#254 terminal Success-collision and staging isolation:** The real streaming Consumer checks pending TODO vs prior Success basename after an empty claim pass, regardless of producer_done, and signals shared blocked event with fixed `QueueClaimSuccessConflictError`. Producer's terminal backpressure/drain guards and Orchestrator's failed teardown then work for both successful claim rollback and unclaimable preexisting Success (no fabricated Worker). Success publication stages content in a sibling `.success-publish-staging` outside the outermost Success ancestor, retaining atomic same-volume link into Success. A cleanup-denied staged orphan is not enumerated by recursive Success-only merges; ordinary output, identity and report semantics remain unchanged.
