# Queue recovery and Worker Success preservation (phase 2c)

## RUNNING → TODO recovery

The production `recover_running_to_todo(item_dirs)` API keeps its integer return value (completed real moves only). For each normal or nested RUNNING file it now uses the same exclusive, inode-verified hardlink + source unlink helper as accepted PR #253's TODO→RUNNING claims. If a destination TODO file/symlink already exists, the source is aliased, the filesystem cannot hardlink, the unlink fails, or a competing recovery wins, **do not overwrite** the prior TODO. Leave the RUNNING file intact where possible; a crash between hardlink and unlink may leave both paths and is **not** counted as recovered. Only successful moves emit the existing best-effort `requeued` event, never a logical retry-family or HTTP request.

The existing public two-tuple `pick_and_claim_next_prompts` result and optional exact claim receipt mapping are unchanged. Additionally, a preexisting `Success/<basename>` now prevents a new flattened TODO→RUNNING claim for that basename. This avoids adopting an old output as proof that a new Worker already completed. Disambiguate or explicitly reset prior Success before retrying; this policy does not remove either conflicting source or result.

## Worker Success publication

Direct `PromptAPIPipeline.proc` Success writes (real LLM and explicitly configured mock mode) use `publish_success_text_no_clobber`, which writes a unique same-directory UTF-8 temp file and fsyncs it, then publishes its inode with atomic exclusive `os.link`. Prior Success files, including symlinks, cannot be replaced. An existing Success raises a file-exists persistence error to the existing Worker exception path, and RUNNING is not unlinked. Successfully published Success is followed by existing `record_success_identity` and optional RUNNING cleanup semantics. A competing writer can win only once; no unsafe `os.replace` fallback for filesystems lacking hardlinks. Unique staging files are unlinked on conflict, not counted as published output. The explicit oldest alternative legacy Worker code path is updated too.

## Limits

Exclusive hardlink publication does **not** provide a cross-process transaction for the subsequent unlink, nor prove a persistent source generation, trusted Retry Family, end-to-end exactly-once processing, or acknowledged ES/SQL sink. A successful Success publication can precede a crash in identity bookkeeping or cleanup and requires existing recovery logic; the result and source may coexist, but neither is silently overwritten. Uncooperative writers, filesystem TOCTOU, manually staged symlinks, nested stage orchestration, intentionally forced overwrite workflows, Windows/SMB hardlink support and other Success writers outside `PromptAPIPipeline.proc` are separate acceptance/safety surfaces. Preserve input and operator evidence rather than auto-fixing conflicting files.

Hosted Linux offline E2E runs actual file-based recovery, nested and conflicting TODO, staged output collisions and competing writers, plus isolated real Worker calls and all established queue/quality/archive regressions. Windows/Ollama/ES/SQL real host operator acceptance remains deferred.

**Codex P1 race correction (2026-10-29):** A prior Success check alone is insufficient: the older Worker might publish Success and unlink its prior RUNNING between that check and a new claimant's exclusive RUNNING creation. Therefore the picker rechecks the same Success basename **after** completing the no-overwrite claim and **before** emitting the claim receipt or dispatching. If the old Success appeared, the new RUNNING source is exclusively restored to its original TODO path and is **not** dispatched, not counted, and not marked successful. A failed safe restoration raises a payload-free error and retains the ambiguous files for operator inspection rather than emitting an invented claim. The regression uses two actual threads with a deliberately paused claim and an actual older Worker publication.

**Codex P2 cleanup correction:** Once the Success hardlink has been successfully published, cleanup of its expendable `.success-*.tmp` staging link is best-effort. An OSError on this cleanup cannot retroactively fail the committed Worker output or suppress success-identity bookkeeping/RUNNING cleanup. The staging link may remain pending operator cleanup; original publication exceptions (e.g. existing Success) also stay authoritative. Actual isolated Worker regression deliberately denies temporary unlink and checks that Success remains committed, Worker reports successful completion, and any orphan staging link remains visible.

**Second formal Review P2 — terminal rollback failure:** If a previous Success appears after the fresh no-clobber claim, but the attempted exclusive RUNNING→original TODO restoration fails, the queue raises a dedicated payload-free `QueueClaimRollbackError` and preserves files for operator recovery. The real streaming consumer catches only this typed terminal error around its actual `pick_and_claim_next_prompts` call, sets `ctx._queue_claim_blocked_event`, and re-raises to the pre-existing `CONSUMER_TERMINATED` incident handler. The SQL/Table/ES coordinator already watches this blocked event when the producer finishes and then performs terminal failed shutdown (including Row Merger release), avoiding a pending-work deadlock. No claim UUID is emitted, and the old Success is never asserted to be the fresh source's output. The new real-file consumer test publishes the older result during fresh claim and denies the rollback, then verifies the coordinator signal, retained fresh RUNNING bytes, old Success intact, and zero observed claims.

**Third formal Review P2 — Producer backpressure:** A terminal claim rollback can happen before all producer rows are scheduled. The actual SQL/Table/ES producer's after-scheduling `outstanding > low` loop, its final drain loop, and shared `producer_backpressure_wait` previously ignored the blocked-queue event. Even when Consumer signalled rollback failure, the producer could await permanently-undrainable work until hard timeouts (possibly six hundred seconds) before its completion flag was set. The producer now checks the same terminal `ctx._queue_claim_blocked_event` during its bounded scheduling, backpressure and drain checks, stops scheduling further rows and exits without pretending `progress.prod_done=true`. The `_producer_main` wrapper's separate thread-completion flag is set in `finally`, allowing existing Orchestrator to classify terminal failure, perform safe Row Merger teardown and retain evidence. This does not turn terminal queue error into user cancellation or normal producer success. An isolated invocation of actual `produce_rows` with persistent outstanding and a signalled event, and actual `producer_backpressure_wait`, verify exit and false progress completion.
