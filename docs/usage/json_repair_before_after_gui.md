# Windows GUI：JSON 修復前後差異（按需浮動視窗）

在「Processing Quality／異常監控」摘要右側，當本次 Run
已記錄到修復嘗試或成功的 JSON 前後比較時，才顯示 **🔎 JSON 差異 (n)**。
點擊後開啟獨立的可調整大小視窗；沒有 JSON 修復的任務，
**主畫面不再保留常駐比較表格區塊**。

浮動視窗以可橫向／縱向捲動、依 DPI 字體高度調整列高的表格，
顯示最多 12 個最近成功修復事件：時間、`run_id`、
**工作項目提示碼**、**切片追蹤提示碼**、12 碼**單次修復事件 ID**、
推測類型、原始→修復字元數、首次解析錯誤相對位置、
詞法字面值相同率、**疑似鍵名片段數**（前→後）。

## 為何不同文件都有 TODO/1.txt？如何避免顯示成同一切片？

舊品質事件只保留原始 `slice_id` 的檔名（`Path(...).name`），
因此不同工作項目 `A/TODO/1.txt`、`B/TODO/1.txt` 都變成 `1.txt`，
即使將此檔名 SHA-256 從 8 碼延長成完整 64 碼，也無法找回丟失的來源身分。

**本次修正僅對新寫入的 slice 品質事件有效**：在把路徑裁成
檔名前，先取得 `TODO`／`RUNNING`／`Success` 的父層
**工作項目位置**與切片檔名。分別計算兩個獨立的、24 字元
SHA-256 十六進位提示碼：
- `work_item_hint`：正規化工作項目位置的指紋。
- `slice_trace_hint`：工作項目位置與切片檔名的組合指紋。

同一工作項目的 `TODO/1.txt` → `RUNNING/1.txt` →
`Success/1.txt` 會保持相同追蹤提示碼；不同工作項目的
`1.txt` 會產生不同提示碼。品質 JSONL **只保存提示碼與舊欄位
`slice_id: "1.txt"`，不記錄完整路徑或 Prompt 內容**。

這些值只是**同一位置的診斷指紋**，不是經過來源資料庫驗證的
`document_id` 或永久 UUID；若移動／更名工作項目、切片被同名
覆寫、跨主機相對路徑或目錄別名，仍可能失去連續性。
SHA-256 也不是路徑加密，已知可能路徑時仍可能猜測指紋，
所以品質事件應維持原有的私有存取控制。

對舊品質紀錄，GUI 的工作項目欄位會明示 **「舊紀錄：僅檔名」**，
保留其原本的檔名雜湊供查找，但不假稱能推回工作項目。
對不符合支援路徑格式的單獨輸入，也會採相同降級表示。

`run_id` 識別執行，`event_id` 識別每一次修復；
兩者並不等於不同文件數。本改動只修正品質可觀測性，
不更動 TODO／RUNNING Queue claim、來源檔內容、Retry、修復
或 ES／SQL 寫回策略。

## 快速變動圖（非語意 Diff）

選取案例後，圖中原始／修復兩條水平色帶分別表示：
藍色＝兩者相同的前綴與後綴字元範圍，橘色＝其餘改動或無法確認的中段。
即使字面值相同率為 95%，前後文字長度仍可不同，這不矛盾：
總長度計入 JSON 結構與格式字元；字面值同率則是詞法
token 順序與匹配字元的啟發式估計，不是字元總長度比例。

「疑似鍵名片段數」為詞法掃描符合類似帶引號的 `"key":`
形式的**出現次數**，不是唯一 `dict` key 數量，也不是通過
JSON parse 的 schema 欄位數。首次錯誤位置為解析器相對原文的
百分比，不是錯誤發生率。

## 隱私與後續的原文差異檢視

此 PR **不新增原始 JSON 內容紀錄**。現有 Worker 能在修復當下
同時拿到原始及修復後的文字，但原有品質事件只保存固定代碼及數值；
歷史事件中的完整原文已無法從摘要還原。

提供可點選案例並直接查看完整 before/after 文字及語意／行內差異，
需要一條額外的、經審查的**明確 opt-in 本機私有原文快照**：
限制路徑和檔案權限、每 Run 容量／保留上限、禁止上傳到品質 JSONL
或 GitHub、確認按鈕與刪除功能，且必須以同次修復事件 ID
精確連結，不可依相同切片提示碼猜測。此功能應獨立 PR 處理，
不能預設開啟，也不能把現有品質日誌的隱私護欄拆掉。

詞法比較與圖示不保證修復後語意、日期、Event／Event_Timeline、
完整來源或 SQL／ES Sink 正確；模型輸出只通過 JSON parse
不代表沒有截斷。此 GUI 改動不影響 Prompt、模型、Queue、重跑與寫回。
