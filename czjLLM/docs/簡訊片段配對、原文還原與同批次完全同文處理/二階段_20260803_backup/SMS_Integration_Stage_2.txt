不要走SRA_REPORT，而是使用LLM背景能力，用PURE_LLM模式，執行下列任務：

你是一個「簡訊內容模板辨識、個人化變數正規化、輕微傳輸雜訊容錯收攏與代表性原始紀錄追溯引擎」。

輸入資料是前一階段產生的一個合法 JSON 物件，主要結構如下：

{
"Messages": [
{
"MessageID": "MSG000001",
"Address1": "來源端識別資訊",
"RecoveredContent": "已完成片段還原及完全同文收攏的簡訊正文",
"ConfirmedOccurrenceCount": 1,
"CoveredIncompleteOccurrenceCount": 0,
"ReviewRequired": false,
"ReviewReason": null,
"Occurrences": [
{
"OccurrenceID": "MSG000001-OCC001",
"Address2": "目的端識別資訊",
"StartTime": "2026-07-20T08:00:05",
"EndTime": "2026-07-20T08:00:05",
"AssemblyStatus": "single",
"RawIDs": [
"原始資料識別碼"
],
"BoxNos": [],
"Channels": []
}
]
}
],
"UnresolvedOccurrences": []
}

每一個 `Messages` 陣列中的物件，代表一種已完成片段還原及第一階段完全同文收攏的簡訊正文。

你的主要任務是將文字主體、通知目的及應採取行動相同，只有個人化變數、格式差異或極輕微傳輸雜訊不同的 Message，收攏成同一個模板群組，以便快速掌握本批資料包含哪些簡訊類型。

此外，為避免自動化串接完成後遺失第一階段中間產物，每個模板群組還必須從正式 Message 的 `Occurrences` 中，保留少量具有代表性的原始紀錄，輸出於 `TraceSamples`，供後續依 RawID 快速反查。

`TraceSamples` 只供追溯，不得作為模板辨識、收攏、分類或計數依據。

# 一、輸入資料使用規則

## 1. 正式模板來源

只使用最外層 `Messages` 陣列中的物件建立正式模板群組。

每個 Message 進行模板辨識時，主要使用下列欄位：

* `MessageID`
* `Address1`
* `RecoveredContent`
* `ConfirmedOccurrenceCount`
* `CoveredIncompleteOccurrenceCount`
* `ReviewRequired`
* `ReviewReason`

`Occurrences` 中的資料不得用來建立或拆分模板。

不得因下列 Occurrence 層級欄位不同，而建立不同模板：

* `RawIDs`
* `BoxNos`
* `Channels`
* `Address2`
* `OccurrenceID`
* `StartTime`
* `EndTime`
* `AssemblyStatus`

上述 Occurrence 層級欄位只能在模板分群全部完成後，依本提示的追溯抽樣規則，選入 `TraceSamples`。

## 2. 追溯資料不得反向影響分群

不得因為下列情況而合併或拆分模板：

* RawID 相同或不同。
* Address2 相同或不同。
* BoxNo 相同或不同。
* Channel 相同或不同。
* Occurrence 發生時間相近或相隔較遠。
* 同一 Message 具有大量 Occurrences。
* 不同 Message 的 Occurrence 數量不同。

模板分群只能依：

* `RecoveredContent`
* 文字主體與句型結構
* 通知目的
* 事件狀態
* 對收件人的行動要求
* 允許的個人化變數
* 符合規則的輕微傳輸雜訊
* 必要時參考 `Address1` 所代表的服務身分

進行判斷。

## 3. UnresolvedOccurrences 規則

最外層 `UnresolvedOccurrences` 不得用來：

* 建立正式模板。
* 補齊正式 Message 的文字。
* 推測缺少的正文。
* 增加 `TotalOccurrenceCount`。
* 增加 `DistinctContentCount`。
* 增加 `TotalCoveredIncompleteOccurrenceCount`。
* 納入任何正式模板群組。
* 加入 `TraceSamples`。

不得把 unresolved 片段強制掛入任何模板群組。

不得把任何 `UnresolvedOccurrenceID`、其 RawID 或其他欄位放入正式模板群組。

## 4. ReviewRequired 規則

若某個 Message 的 `ReviewRequired` 為 true，原則上應單獨形成模板群組，不得與其他 Message 強制收攏。

只有在下列條件全部成立時，才可將其與其他 Message 收攏：

1. `RecoveredContent` 本身完整且可直接使用。
2. `ReviewReason` 只涉及時間、批次或非正文欄位問題。
3. 不涉及正文缺漏、片段順序、錯誤配對或文字歸屬不確定。
4. 與其他 Message 的模板關係明確，不需要補字或猜測。

若 `ReviewReason` 可能影響正文內容或訊息歸屬，必須單獨輸出。

# 二、模板收攏的基本條件

只有在下列條件全部成立時，才可收進同一個模板群組：

1. 文字主體及句型結構相同。
2. 通知目的相同。
3. 對收件人的要求或應採取行動相同。
4. 成功、失敗、取消、改期、警告、提醒等狀態相同。
5. 差異只存在於允許的個人化變數、無關緊要的格式差異或符合本提示規則的極輕微傳輸雜訊。
6. 不需要補入整個詞語、短句或句子，才能視為相同模板。
7. 沒有其他證據顯示它們是不同事件、不同服務或不同通知類型。

`Address1` 相同可作為強烈的收攏依據，但不得只因 Address1 相同就強制收攏。

若 Address1 不同，只有在句型、通知目的、行動要求及服務身分仍明確相同，且差異只屬允許變數或輕微雜訊時，才可收攏。

若正文中出現不同的公司、銀行、政府機關、商店、平台或服務名稱，原則上不得只因句型相似就收攏。

# 三、可以收攏的個人化變數差異

下列欄位不同，但其餘句型、通知目的及行動要求相同時，可以收攏：

* 驗證碼。
* 一次性密碼。
* 交易序號。
* 訂單編號。
* 案件編號。
* 帳號末碼。
* 卡號末碼。
* 金額。
* 日期。
* 時間。
* 電話號碼。
* 車牌。
* 發票號碼。
* 取件碼。
* 查詢碼。
* 收件人姓名。
* 門市或服務地點。
* 短網址中的個人化參數。
* 其他可明確辨識的個人化代碼。

例如：

「您的驗證碼為059503，請於五分鐘內輸入，切勿提供給任何人。」

「您的驗證碼為507328，請於五分鐘內輸入，切勿提供給任何人。」

應收攏為：

「您的驗證碼為{驗證碼}，請於五分鐘內輸入，切勿提供給任何人。」

## 固定數字不得誤判為變數

若某個數字在同一模板的各則簡訊中固定不變，且屬於句型本身，不得任意替換成占位符。

例如：

「請於五分鐘內輸入」

其中的「五分鐘」若在各則簡訊中固定相同，應保留原文，不得改成：

「請於{時間}內輸入」

## 日期及時間的特殊規則

日期或時間可以作為一般個人化變數，但若日期或時間本身決定事件身分、事件批次或應採取的行動，則不得任意收攏。

例如下列情況應保守處理：

* 不同日期的停水或停電事件。
* 不同場次的活動通知。
* 活動取消與活動改期。
* 不同到期日且到期日是分析重點。
* 不同災害警報時間。
* 不同預約時段且收件人需採取不同安排。

# 四、允許的輕微傳輸雜訊

短訊在傳送、轉碼、儲存或匯出過程中，可能出現少量亂碼、替代字元或單一字元錯漏。

只有在符合本節全部條件時，才可將這類差異視為同一模板。

## 1. 可以容許的雜訊類型

可以容許：

* 單一替代字元，例如 `�`、`□` 或無法辨識字元。
* 單一控制字元或不可見字元。
* 單一字元遺漏。
* 單一字元重複。
* 單一字元錯置。
* 單一字元被錯誤轉碼。
* 極少量標點、空白、全形半形或換行差異。
* 局部出現一小段明顯的編碼亂碼，但前後句型仍可唯一對應。

通常只允許一至二個局部字元位置存在異常。

較長簡訊即使有兩個以上異常，異常範圍也不得超過非變數正文的約百分之三，且不得集中形成整個缺失詞語、短句或句子。

## 2. 必須存在乾淨版本佐證

只有在同一候選模板群組中，存在至少一則較完整、較清楚且無該亂碼的 Message，可以直接證明原本句型時，才可將亂碼版本收進該模板。

例如：

「您的驗證碼為059503，請於五分鐘內輸入，切勿提供給任何人。」

「您的驗證碼為507328，請於五分�內輸入，切勿提供給任何人。」

可以收攏為：

「您的驗證碼為{驗證碼}，請於五分鐘內輸入，切勿提供給任何人。」

因為第一則乾淨版本可直接佐證「五分鐘」的正確文字。

若只有一則含亂碼的簡訊，且沒有任何乾淨版本或其他明確證據，不得自行猜測亂碼原字。

該簡訊應保留原文，單獨形成模板群組。

## 3. 亂碼只用於比較，不得修改原始樣本

進行模板比對時，可以在內部忽略零寬字元、控制字元或明顯編碼雜訊。

但：

* `TraceSamples` 中的 `RecoveredContent` 必須直接複製輸入中的原始值。
* 不得在 `TraceSamples` 中偷偷修正亂碼。
* 不得將原文中的「門市」改寫成「門店」或進行其他同義詞改寫。
* 不得修改 MessageID。
* 不得修改 OccurrenceID。
* 不得修改 RawID。
* 不得自行新增不存在的文字。
* 不得把某一則簡訊的文字或追溯資料移到另一則簡訊中。

輸出前必須對每一筆 `TraceSamples[].RecoveredContent` 與其來源 Message 的原始 `RecoveredContent` 執行逐字精確比對。

只要字元、標點、空白、全形半形或換行與輸入不同，即視為輸出錯誤。

## 4. TemplateContent 的亂碼修復規則

若群組中存在乾淨版本，`TemplateContent` 應採用乾淨版本中最有支持的正常句型。

選擇規則依序為：

1. 優先使用沒有亂碼且正文最完整的版本。
2. 多個乾淨版本相同時，使用出現次數最多的版本。
3. 若出現次數相同，使用 MessageID 排序最前的版本。
4. 再將個人化欄位替換成具名占位符。

只能依群組內其他乾淨版本修復亂碼。

不得依常識自行猜字。

若群組內沒有任何乾淨版本，不得修復，應保留原始文字並單獨形成模板群組。

## 5. 下列不是輕微傳輸雜訊

下列情況不得視為輕微亂碼或位元錯漏：

* 缺少整個詞語。
* 缺少整個短句或句子。
* 多個連續文字區段消失。
* 句首或句尾大段缺漏。
* 需要從其他簡訊補入整段內容。
* 文字順序大幅改變。
* 同時存在多處無法確定的異常。
* 差異可能改變通知目的、事件或應採取行動。
* 無法確定是傳輸錯誤還是原始正文差異。

這類情況不得因為「看起來很像」就收攏。

# 五、關鍵語意差異保護

即使只差一個字元，只要差異可能改變語意，就不得當作亂碼收攏。

下列文字及其上下文屬於關鍵語意，不得模糊處理：

* 不、未、無、勿、免、非、禁止等否定詞。
* 已、尚未、成功、失敗、完成、取消、改期、退款、扣款等狀態詞。
* 停水、停電、停氣、維修、故障、詐騙、促銷等事件詞。
* 立即、無須、必須、避免、請勿等行動要求。
* 金額。
* 日期。
* 時間。
* 帳號或卡號。
* 驗證碼或一次性密碼。
* 訂單、案件、交易及其他識別碼。
* 網址或電話。
* 地點。
* 公司、機關、銀行、商店或服務名稱。

例如：

「交易成功」與「交易失敗」不得收攏。

「今日停水」與「今日停電」不得收攏。

「請點擊下列網址」與「請勿點擊下列網址」不得收攏。

即使「請勿」中的「勿」疑似遺漏，也不得自動假設是亂碼，因為這會改變行動要求。

若異常字元位於個人化變數範圍，例如驗證碼或交易序號中，可將整個欄位替換成相應占位符，但不得嘗試修復實際變數值。

# 六、不得收攏的情況

即使文字高度相似，只要通知目的、事件狀態或應採取行動不同，就不得收攏。

例如：

* 申請成功與申請失敗。
* 交易成功與交易失敗。
* 已扣款與退款完成。
* 今日停水與今日停電。
* 活動取消與活動改期。
* 要求立即處理與一般資訊通知。
* 詐騙警告與促銷廣告。
* 繳費成功與繳費逾期。
* 包裹到店與包裹退回。
* 帳戶登入成功與可疑登入警告。
* 密碼已變更與要求變更密碼。
* 不同品牌、機構或服務的獨立通知。
* 日期、時間或地點本身代表不同事件。
* 一則內容完整，另一則缺少整段重要文字。
* 需要補字、刪字、改寫或摘要後，才能看起來相同。
* 只有大量共同詞語，但句型骨架或通知目的不同。

不得只依：

* 關鍵詞重疊。
* 字串相似度。
* 編輯距離。
* 相同 Address1。
* 相近時間。
* 相同 Category。

就強制收攏。

# 七、TemplateContent 規則

`TemplateContent` 必須保留原本句型，只將實際變動的個人化欄位替換為具名占位符。

允許使用：

* `{驗證碼}`
* `{一次性密碼}`
* `{金額}`
* `{日期}`
* `{時間}`
* `{交易序號}`
* `{訂單編號}`
* `{案件編號}`
* `{帳號末碼}`
* `{卡號末碼}`
* `{網址}`
* `{電話}`
* `{地點}`
* `{姓名}`
* `{車牌}`
* `{發票號碼}`
* `{取件碼}`
* `{查詢碼}`
* `{其他代碼}`

不得使用：

* `{變數1}`
* `{變數2}`
* `{值}`
* `{內容}`
* `XXX`
* `****`
* 無法辨識其用途的任意占位符。

若某段內容只在一則簡訊中出現，且無法確定是個人化變數、亂碼或正文差異，不得擅自替換成占位符。

若同一欄位的格式或長度不同，但用途明確相同，仍可使用同一具名占位符。

例如：

* `P009799203`
* `TX-20260720-9981`
* `A771208`

若上下文均明確表示交易序號，可統一替換為 `{交易序號}`。

# 八、Category 規則

`Category` 應依簡訊的主要通知目的，輸出簡短且可理解的中文類別名稱。

例如：

* 驗證碼通知
* 一次性密碼通知
* 信用卡消費通知
* 繳費成功通知
* 訂單到店通知
* 包裹取件通知
* 系統維護通知
* 停電通知
* 停水通知
* 交易失敗通知
* 詐騙警告
* 活動異動通知

Category 不得只寫：

* 通知
* 簡訊
* 其他
* 一般訊息

除非確實無法辨識通知目的。

Category 相同不代表一定可以收攏；仍須符合正文模板、通知目的及行動要求規則。

# 九、計數規則

## 1. MessageCount

等於該模板群組中不同 MessageID 的數量。

## 2. DistinctContentCount

等於該模板群組中，逐字不同的 `RecoveredContent` 數量。

不得直接以 MessageID 數量代替。

若兩個不同 MessageID 的 RecoveredContent 完全相同：

* `MessageCount` 計為 2。
* `DistinctContentCount` 計為 1。

## 3. TotalOccurrenceCount

等於群組內所有 Message 的 `ConfirmedOccurrenceCount` 總和。

不得：

* 直接計算 MessageID 數量。
* 使用 `TraceSamples` 的筆數代替。
* 加入 `CoveredIncompleteOccurrenceCount`。
* 加入 `UnresolvedOccurrences`。
* 因為 TraceSamples 只抽取部分 Occurrence，就降低總數。

## 4. TotalCoveredIncompleteOccurrenceCount

等於群組內所有 Message 的 `CoveredIncompleteOccurrenceCount` 總和。

此欄位只表示另有多少次已被完整正文涵蓋的不完整發送紀錄。

不得加入 `TotalOccurrenceCount`。

## 5. MinorCorruptionVariantCount

等於該模板群組中，必須依靠「輕微傳輸雜訊容錯規則」才能與乾淨版本收攏的 Message 數量。

只有個人化變數不同，不計入此欄位。

只有標點、一般空白或全形半形差異，若不涉及真正亂碼或字元錯漏，也不必計入。

`MinorCorruptionVariantCount` 計算的是 Message 數量，不是 Occurrence 數量，也不是 RawID 數量。

# 十、代表性原始紀錄追溯規則

## 1. TraceSamples 的用途

每個模板群組必須輸出 `TraceSamples`，保留少量可直接反查原始資料的代表性樣本。

`TraceSamples` 的用途只有：

1. 證明該模板所依據的原始 `RecoveredContent` 確實存在於輸入資料。
2. 提供可回查原始簡訊片段的 RawID。
3. 若模板包含輕微亂碼，保留乾淨版本與亂碼版本作為收攏證據。

`TraceSamples` 不是完整明細，不要求列出所有 Message、所有正文變體或所有 Occurrence。

`TraceSamples` 不得影響：

* 模板分群。
* `TemplateContent`。
* `Category`。
* `MessageCount`。
* `DistinctContentCount`。
* `TotalOccurrenceCount`。
* `TotalCoveredIncompleteOccurrenceCount`。
* `MinorCorruptionVariantCount`。

## 2. TraceSamples 的輸出格式

每一筆 TraceSample 只能輸出下列兩個欄位：

{
"RecoveredContent": "輸入中的原始 RecoveredContent",
"RawIDs": [
"同一個 Occurrence 的全部原始 RawID"
]
}

不得在 TraceSamples 中輸出：

* MessageID。
* Address1。
* Address2。
* OccurrenceID。
* StartTime。
* EndTime。
* BoxNos。
* Channels。
* Confidence。
* AssemblyStatus。
* ReviewReason。
* 其他未指定欄位。

MessageID、OccurrenceID、Address1、Address2、時間、Channel 及 BoxNo 可在內部用於定位來源與完成稽核，但不得出現在最終輸出。

## 3. RecoveredContent 保真規則

每一筆 `TraceSamples[].RecoveredContent` 必須直接逐字複製自正式 Message 的原始 `RecoveredContent`。

不得：

* 修正亂碼。
* 補字或刪字。
* 改寫句子。
* 替換同義詞。
* 統一標點。
* 修改空白、全形半形或換行。
* 將「門市」改成「門店」。
* 將「7月26日前」改成「7月26前」。
* 使用 `TemplateContent` 取代原始 `RecoveredContent`。
* 將某一個 Message 的正文配給另一個 Message 的 RawID。

只要輸出的 `RecoveredContent` 與輸入原文有任何字元差異，即視為輸出錯誤。

## 4. RawIDs 保真規則

每一筆 TraceSample 的 `RawIDs` 必須取自該 `RecoveredContent` 所屬正式 Message 之下的同一個 Occurrence。

若被選中的 Occurrence 包含多個 RawID，必須完整保留該 Occurrence 的全部 RawID。

不得：

* 只保留 Multipart Occurrence 的部分 RawID。
* 混合不同 Occurrence 的 RawID。
* 混合不同 Message 的正文與 RawID。
* 修改 RawID。
* 重新排序 RawID。
* 自行新增或推測 RawID。
* 使用最外層 `UnresolvedOccurrences` 的 RawID。

## 5. TraceSamples 抽樣數量

每個模板群組最多保留三筆 TraceSample。

### 5.1 一般單一正文模板

若 `DistinctContentCount` 等於 1：

* 原則上只保留一筆 TraceSample。
* 即使該 Message 有大量重複 Occurrences，也不得因重複發送而增加 TraceSamples。
* 從該 Message 中選取一個具有完整 RawIDs 的正式 Occurrence即可。

### 5.2 多個個人化正文變體

若 `DistinctContentCount` 大於 1，且差異只來自訂單編號、日期、時間、金額、代碼或其他允許的個人化變數：

* 原則上保留兩筆不同 `RecoveredContent` 的 TraceSample。
* 優先選擇最能呈現個人化欄位差異的兩個正文。
* 不需要把所有正文變體全部輸出。
* 若實際只有一筆具有可用 RawIDs，則只輸出一筆，不得虛構第二筆。

### 5.3 輕微亂碼模板

若 `MinorCorruptionVariantCount` 大於 0：

1. 必須優先保留一筆乾淨版本。
2. 必須優先保留一筆因輕微傳輸雜訊而收攏的原始亂碼版本。
3. 若存在另一種具有辨識價值的不同亂碼類型，可再保留一筆。
4. 總數不得超過三筆。

亂碼版本的 `RecoveredContent` 必須保留原始異常，不得在 TraceSamples 中修復。

若同一模板同時具有個人化變數差異與亂碼差異，應優先確保乾淨版與亂碼版均被保留，而不是單純選擇兩個乾淨的個人化版本。

### 5.4 單獨成群的亂碼版本

若只有一個含亂碼的 Message，且沒有乾淨版本佐證：

* 該 Message 必須單獨形成模板群組。
* `TemplateContent` 不得自行修復亂碼。
* TraceSamples 保留一筆原始亂碼正文及其 RawIDs。

## 6. 候選 Occurrence 選擇順序

若同一個 Message 有多個 Occurrence 可供選擇，依下列順序選取一個：

1. 優先選擇 `RawIDs` 非空的 Occurrence。
2. 優先選擇 `AssemblyStatus` 為 `complete` 或 `single`，且 RawIDs 完整的 Occurrence。
3. 優先選擇輸入順序較前的 Occurrence。
4. 若仍無法區分，選擇 `StartTime` 較早者。
5. 若仍無法區分，選擇 OccurrenceID 排序較前者。

不得因 Address2、Channel、BoxNo 或發送時間不同，而額外增加 TraceSamples。

## 7. 無可用追溯資料的處理

若某個正式模板群組中的所有 Message 均沒有可用 Occurrence，或所有 Occurrence 的 `RawIDs` 均為空：

* `TraceSamples` 輸出空陣列 `[]`。
* 不得虛構 RawID。
* 不得使用 UnresolvedOccurrences 補足。
* 其他模板欄位與計數仍照正式 Message 計算。

# 十一、輸出要求

每個模板群組只輸出一個物件。

每個模板群組只能輸出下列欄位：

* `TemplateContent`
* `Category`
* `MessageCount`
* `DistinctContentCount`
* `TotalOccurrenceCount`
* `TotalCoveredIncompleteOccurrenceCount`
* `MinorCorruptionVariantCount`
* `TraceSamples`

不得輸出：

* `MessageIDs`
* `VariantSamples`
* Address1
* Address2
* MessageID
* OccurrenceID
* StartTime
* EndTime
* BoxNos
* Channels
* Confidence
* AssemblyStatus
* 完整 Occurrences
* 任何 UnresolvedOccurrences 內容

MessageID 仍須在內部使用，以確保每一個正式 Message 只歸入一個模板群組，但不得出現在最終輸出。

最終只能輸出一個合法 JSON 陣列，不得輸出 Markdown、程式碼區塊、分析過程、前言、結語或任何 JSON 陣列以外的文字。

限制：

1. 每個模板群組只輸出一個物件。
2. 不得重複輸出相同 `TemplateContent`。
3. 無法合理收攏的 Message，必須單獨形成模板群組。
4. 不得使用 UnresolvedOccurrences 建立模板、增加計數或建立 TraceSamples。
5. `MessageCount` 必須等於群組內不同 MessageID 的數量。
6. `DistinctContentCount` 必須依群組內逐字不同的 `RecoveredContent` 計算。
7. `TotalOccurrenceCount` 必須等於群組內所有 Message 的 `ConfirmedOccurrenceCount` 總和。
8. 不得將 `CoveredIncompleteOccurrenceCount` 加入 `TotalOccurrenceCount`。
9. `TotalCoveredIncompleteOccurrenceCount` 必須等於群組內所有 Message 的 `CoveredIncompleteOccurrenceCount` 總和。
10. `MinorCorruptionVariantCount` 必須等於因輕微傳輸雜訊規則而被收攏的 Message 數量。
11. `MinorCorruptionVariantCount` 計算 Message 數量，不是 Occurrence 或 RawID 數量。
12. 若 `MinorCorruptionVariantCount` 大於 0，必須存在至少一個乾淨版本作為收攏依據。
13. 若同群組存在乾淨版與亂碼版，TraceSamples 必須優先各保留至少一筆。
14. `TraceSamples` 最多保留三筆。
15. `DistinctContentCount` 等於 1 時，原則上只保留一筆 TraceSample。
16. 多個個人化正文變體原則上只保留兩筆不同正文。
17. TraceSamples 的數量不得影響任何計數欄位。
18. `TraceSamples[].RecoveredContent` 必須與輸入原文逐字相等。
19. `TraceSamples[].RawIDs` 必須完整取自同一個正式 Occurrence。
20. 不得混合不同 Message 或不同 Occurrence 的正文與 RawID。
21. 不得因輸出中沒有 MessageIDs，就遺漏、重複使用或重複歸類任何正式 Message。
22. `TemplateContent` 只能依實際輸入及同群組乾淨版本建立，不得自行補寫新句子。
23. 不得因一至兩個關鍵語意字元不同，就當作亂碼收攏。
24. 模板群組依其中最早出現的 MessageID 排序。
25. 最終不得輸出 JSON 陣列以外的文字。

# 十二、最終稽核

輸出前必須逐項檢查：

1. 每一個最外層 `Messages` 中的 MessageID，必須且只能在內部分配到一個模板群組。
2. 不得遺漏任何正式 Message。
3. 不得使用任何 UnresolvedOccurrence 建立模板或 TraceSamples。
4. 同一模板群組中的所有 Message，通知目的、事件狀態及行動要求必須相同。
5. 若移除占位符對應的個人化變數後，剩餘句型仍存在重要差異，不得收攏。
6. TemplateContent 中的每個占位符都必須有明確欄位用途。
7. 若亂碼位於否定詞、狀態詞、事件詞或行動要求位置，不得自動收攏。
8. 若只有單一亂碼版本且沒有乾淨版本佐證，不得自行修復或與其他模板合併。
9. MinorCorruptionVariantCount 必須與實際因亂碼容錯而收攏的 Message 數量一致。
10. MessageCount、DistinctContentCount、TotalOccurrenceCount 及 TotalCoveredIncompleteOccurrenceCount 必須可由輸入重新計算。
11. 每一筆 TraceSample 的 RecoveredContent 必須真實存在於正式 Messages。
12. 每一筆 TraceSample 的 RawIDs 必須真實存在於該正文所屬 Message 的同一個 Occurrence。
13. 被選中的 Occurrence 之 RawIDs 必須完整保留，不得刪減、改寫、重排或跨 Occurrence 混合。
14. TraceSamples 中的 RecoveredContent 必須逐字複製，不得修正、摘要、正規化或改寫。
15. 每個模板群組的 TraceSamples 不得超過三筆。
16. 不得為湊足樣本數而重複相同正文或相同 RawIDs。
17. 若 MinorCorruptionVariantCount 大於 0，應確認 TraceSamples 已優先保留乾淨版與亂碼版。
18. TraceSamples 不得影響模板分群或任何計數。
19. 不得輸出 MessageIDs、VariantSamples、MessageID、OccurrenceID、地址、時間、Channel、BoxNo 或完整 Occurrences。
20. 不得輸出任何 JSON 陣列以外的文字。
