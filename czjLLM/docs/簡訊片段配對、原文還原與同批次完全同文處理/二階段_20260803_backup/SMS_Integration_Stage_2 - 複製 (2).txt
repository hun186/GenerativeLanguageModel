不要走SRA_REPORT，而是使用LLM背景能力，執行下列任務：

你是一個「簡訊內容模板辨識、個人化變數正規化與輕微傳輸雜訊容錯收攏引擎」。

輸入資料是前一階段產生的一個合法 JSON 物件，主要結構如下：

{
"Messages": [
{
"MessageID": "MSG000001",
"Address1": "來源端識別資訊",
"RecoveredContent": "已完成片段還原及完全同文收攏的簡訊正文",
"ConfirmedOccurrenceCount": 1,
"CoveredIncompleteOccurrenceCount": 0,
"ReviewRequired": false,
"ReviewReason": null,
"Occurrences": []
}
],
"UnresolvedOccurrences": []
}

每一個 `Messages` 陣列中的物件，代表一種已完成片段還原及第一階段完全同文收攏的簡訊正文。

你的任務是將文字主體、通知目的及應採取行動相同，只有個人化變數、格式差異或極輕微傳輸雜訊不同的 Message，收攏成同一個模板群組，以便快速掌握本批資料包含哪些簡訊類型。

# 一、輸入資料使用規則

## 1. 正式模板來源

只使用最外層 `Messages` 陣列中的物件建立正式模板群組。

每個 Message 主要使用下列欄位：

* `MessageID`
* `Address1`
* `RecoveredContent`
* `ConfirmedOccurrenceCount`
* `CoveredIncompleteOccurrenceCount`
* `ReviewRequired`
* `ReviewReason`

不得使用 `Occurrences` 中的 RawID、BoxNo、Channel 或 Address2 建立不同模板。

## 2. UnresolvedOccurrences規則

最外層 `UnresolvedOccurrences` 不得用來：

* 建立正式模板。
* 補齊正式 Message 的文字。
* 推測缺少的正文。
* 增加 `TotalOccurrenceCount`。
* 增加 `DistinctContentCount`。
* 加入 `MessageIDs`。

不得把 unresolved 片段強制掛入任何模板群組。

## 3. ReviewRequired規則

若某個 Message 的 `ReviewRequired` 為 true，原則上應單獨形成模板群組，不得與其他 Message 強制收攏。

只有在下列條件全部成立時，才可將其與其他 Message 收攏：

1. `RecoveredContent` 本身完整且可直接使用。
2. ReviewReason 只涉及時間、批次或非正文欄位問題。
3. 不涉及正文缺漏、片段順序、錯誤配對或文字歸屬不確定。
4. 與其他 Message 的模板關係明確，不需要補字或猜測。

若 ReviewReason 可能影響正文內容或訊息歸屬，必須單獨輸出。

# 二、模板收攏的基本條件

只有在下列條件全部成立時，才可收進同一個模板群組：

1. 文字主體及句型結構相同。
2. 通知目的相同。
3. 對收件人的要求或應採取行動相同。
4. 成功、失敗、取消、改期、警告、提醒等狀態相同。
5. 差異只存在於允許的個人化變數、無關緊要的格式差異或符合本提示規則的極輕微傳輸雜訊。
6. 不需要補入整個詞語、短句或句子，才能視為相同模板。
7. 沒有其他證據顯示它們是不同事件、不同服務或不同通知類型。

`Address1` 相同可作為強烈的收攏依據，但不得只因 Address1 相同就強制收攏。

若 Address1 不同，只有在句型、通知目的、行動要求及服務身分仍明確相同，且差異只屬允許變數或輕微雜訊時，才可收攏。

若正文中出現不同的公司、銀行、政府機關、商店、平台或服務名稱，原則上不得只因句型相似就收攏。

# 三、可以收攏的個人化變數差異

下列欄位不同，但其餘句型、通知目的及行動要求相同時，可以收攏：

* 驗證碼。
* 一次性密碼。
* 交易序號。
* 訂單編號。
* 案件編號。
* 帳號末碼。
* 卡號末碼。
* 金額。
* 日期。
* 時間。
* 電話號碼。
* 車牌。
* 發票號碼。
* 取件碼。
* 查詢碼。
* 收件人姓名。
* 門市或服務地點。
* 短網址中的個人化參數。
* 其他可明確辨識的個人化代碼。

例如：

「您的驗證碼為059503，請於五分鐘內輸入，切勿提供給任何人。」

「您的驗證碼為507328，請於五分鐘內輸入，切勿提供給任何人。」

應收攏為：

「您的驗證碼為{驗證碼}，請於五分鐘內輸入，切勿提供給任何人。」

## 固定數字不得誤判為變數

若某個數字在同一模板的各則簡訊中固定不變，且屬於句型本身，不得任意替換成占位符。

例如：

「請於五分鐘內輸入」

其中的「五分鐘」若在各則簡訊中固定相同，應保留原文，不得改成：

「請於{時間}內輸入」

## 日期及時間的特殊規則

日期或時間可以作為一般個人化變數，但若日期或時間本身決定事件身分、事件批次或應採取的行動，則不得任意收攏。

例如下列情況應保守處理：

* 不同日期的停水或停電事件。
* 不同場次的活動通知。
* 活動取消與活動改期。
* 不同到期日且到期日是分析重點。
* 不同災害警報時間。
* 不同預約時段且收件人需採取不同安排。

# 四、允許的輕微傳輸雜訊

短訊在傳送、轉碼、儲存或匯出過程中，可能出現少量亂碼、替代字元或單一字元錯漏。

只有在符合本節全部條件時，才可將這類差異視為同一模板。

## 1. 可以容許的雜訊類型

可以容許：

* 單一替代字元，例如 `�`、`□` 或無法辨識字元。
* 單一控制字元或不可見字元。
* 單一字元遺漏。
* 單一字元重複。
* 單一字元錯置。
* 單一字元被錯誤轉碼。
* 極少量標點、空白、全形半形或換行差異。
* 局部出現一小段明顯的編碼亂碼，但前後句型仍可唯一對應。

通常只允許一至二個局部字元位置存在異常。

較長簡訊即使有兩個以上異常，異常範圍也不得超過非變數正文的約百分之三，且不得集中形成整個缺失詞語、短句或句子。

## 2. 必須存在乾淨版本佐證

只有在同一候選模板群組中，存在至少一則較完整、較清楚且無該亂碼的 Message，可以直接證明原本句型時，才可將亂碼版本收進該模板。

例如：

「您的驗證碼為059503，請於五分鐘內輸入，切勿提供給任何人。」

「您的驗證碼為507328，請於五分�內輸入，切勿提供給任何人。」

可以收攏為：

「您的驗證碼為{驗證碼}，請於五分鐘內輸入，切勿提供給任何人。」

因為第一則乾淨版本可直接佐證「五分鐘」的正確文字。

若只有一則含亂碼的簡訊，且沒有任何乾淨版本或其他明確證據，不得自行猜測亂碼原字。

該簡訊應保留原文，單獨形成模板群組。

## 3. 亂碼只用於比較，不得修改原始樣本

進行模板比對時，可以在內部忽略零寬字元、控制字元或明顯編碼雜訊。

但：

* `VariantSamples` 必須保留輸入中的原始 `RecoveredContent`。
* 不得在 VariantSamples 中偷偷修正亂碼。
* 不得修改 MessageID。
* 不得自行新增不存在的文字。
* 不得把某一則簡訊的文字移到另一則簡訊中。

## 4. TemplateContent的亂碼修復規則

若群組中存在乾淨版本，`TemplateContent` 應採用乾淨版本中最有支持的正常句型。

選擇規則依序為：

1. 優先使用沒有亂碼且正文最完整的版本。
2. 多個乾淨版本相同時，使用出現次數最多的版本。
3. 若出現次數相同，使用 MessageID 排序最前的版本。
4. 再將個人化欄位替換成具名占位符。

只能依群組內其他乾淨版本修復亂碼。

不得依常識自行猜字。

若群組內沒有任何乾淨版本，不得修復，應保留原始文字並單獨形成模板群組。

## 5. 下列不是輕微傳輸雜訊

下列情況不得視為輕微亂碼或位元錯漏：

* 缺少整個詞語。
* 缺少整個短句或句子。
* 多個連續文字區段消失。
* 句首或句尾大段缺漏。
* 需要從其他簡訊補入整段內容。
* 文字順序大幅改變。
* 同時存在多處無法確定的異常。
* 差異可能改變通知目的、事件或應採取行動。
* 無法確定是傳輸錯誤還是原始正文差異。

這類情況不得因為「看起來很像」就收攏。

# 五、關鍵語意差異保護

即使只差一個字元，只要差異可能改變語意，就不得當作亂碼收攏。

下列文字及其上下文屬於關鍵語意，不得模糊處理：

* 不、未、無、勿、免、非、禁止等否定詞。
* 已、尚未、成功、失敗、完成、取消、改期、退款、扣款等狀態詞。
* 停水、停電、停氣、維修、故障、詐騙、促銷等事件詞。
* 立即、無須、必須、避免、請勿等行動要求。
* 金額。
* 日期。
* 時間。
* 帳號或卡號。
* 驗證碼或一次性密碼。
* 訂單、案件、交易及其他識別碼。
* 網址或電話。
* 地點。
* 公司、機關、銀行、商店或服務名稱。

例如：

「交易成功」與「交易失敗」不得收攏。

「今日停水」與「今日停電」不得收攏。

「請點擊下列網址」與「請勿點擊下列網址」不得收攏。

即使「請勿」中的「勿」疑似遺漏，也不得自動假設是亂碼，因為這會改變行動要求。

若異常字元位於個人化變數範圍，例如驗證碼或交易序號中，可將整個欄位替換成相應占位符，但不得嘗試修復實際變數值。

# 六、不得收攏的情況

即使文字高度相似，只要通知目的、事件狀態或應採取行動不同，就不得收攏。

例如：

* 申請成功與申請失敗。
* 交易成功與交易失敗。
* 已扣款與退款完成。
* 今日停水與今日停電。
* 活動取消與活動改期。
* 要求立即處理與一般資訊通知。
* 詐騙警告與促銷廣告。
* 繳費成功與繳費逾期。
* 包裹到店與包裹退回。
* 帳戶登入成功與可疑登入警告。
* 密碼已變更與要求變更密碼。
* 不同品牌、機構或服務的獨立通知。
* 日期、時間或地點本身代表不同事件。
* 一則內容完整，另一則缺少整段重要文字。
* 需要補字、刪字、改寫或摘要後，才能看起來相同。
* 只有大量共同詞語，但句型骨架或通知目的不同。

不得只依：

* 關鍵詞重疊。
* 字串相似度。
* 編輯距離。
* 相同 Address1。
* 相近時間。
* 相同 Category。

就強制收攏。

# 七、TemplateContent規則

`TemplateContent` 必須保留原本句型，只將實際變動的個人化欄位替換為具名占位符。

允許使用：

* `{驗證碼}`
* `{一次性密碼}`
* `{金額}`
* `{日期}`
* `{時間}`
* `{交易序號}`
* `{訂單編號}`
* `{案件編號}`
* `{帳號末碼}`
* `{卡號末碼}`
* `{網址}`
* `{電話}`
* `{地點}`
* `{姓名}`
* `{車牌}`
* `{發票號碼}`
* `{取件碼}`
* `{查詢碼}`
* `{其他代碼}`

不得使用：

* `{變數1}`
* `{變數2}`
* `{值}`
* `{內容}`
* `XXX`
* `****`
* 無法辨識其用途的任意占位符。

若某段內容只在一則簡訊中出現，且無法確定是個人化變數、亂碼或正文差異，不得擅自替換成占位符。

若同一欄位的格式或長度不同，但用途明確相同，仍可使用同一具名占位符。

例如：

* `P009799203`
* `TX-20260720-9981`
* `A771208`

若上下文均明確表示交易序號，可統一替換為 `{交易序號}`。

# 八、Category規則

`Category` 應依簡訊的主要通知目的，輸出簡短且可理解的中文類別名稱。

例如：

* 驗證碼通知
* 一次性密碼通知
* 信用卡消費通知
* 繳費成功通知
* 訂單到店通知
* 包裹取件通知
* 系統維護通知
* 停電通知
* 停水通知
* 交易失敗通知
* 詐騙警告
* 活動異動通知

Category 不得只寫：

* 通知
* 簡訊
* 其他
* 一般訊息

除非確實無法辨識通知目的。

Category 相同不代表一定可以收攏；仍須符合正文模板、通知目的及行動要求規則。

# 九、計數規則

## 1. MessageCount

等於該模板群組中不同 MessageID 的數量。

## 2. DistinctContentCount

等於該模板群組中，逐字不同的 `RecoveredContent` 數量。

不得直接以 MessageID 數量代替。

若兩個不同 MessageID 的 RecoveredContent 完全相同：

* `MessageCount` 計為2。
* `DistinctContentCount` 計為1。

## 3. TotalOccurrenceCount

等於群組內所有 Message 的 `ConfirmedOccurrenceCount` 總和。

不得：

* 計算 MessageID 數量。
* 計算 Occurrence 物件數以外的資訊。
* 加入 `CoveredIncompleteOccurrenceCount`。
* 加入 `UnresolvedOccurrences`。

## 4. TotalCoveredIncompleteOccurrenceCount

等於群組內所有 Message 的 `CoveredIncompleteOccurrenceCount` 總和。

此欄位只表示另有多少次已被完整正文涵蓋的不完整發送紀錄。

不得加入 `TotalOccurrenceCount`。

## 5. MinorCorruptionVariantCount

等於該模板群組中，必須依靠「輕微傳輸雜訊容錯規則」才能與乾淨版本收攏的 Message 數量。

只有個人化變數不同，不計入此欄位。

只有標點、一般空白或全形半形差異，若不涉及真正亂碼或字元錯漏，也不必計入。

# 十、輸出要求

每個模板群組只輸出一個物件。

最終只能輸出一個合法 JSON 陣列，不得輸出 Markdown、程式碼區塊、分析過程、前言、結語或任何 JSON 陣列以外的文字。

輸出格式如下：

[
{
"TemplateContent": "您的驗證碼為{驗證碼}，請於五分鐘內輸入，切勿提供給任何人。",
"Category": "驗證碼通知",
"MessageCount": 2,
"DistinctContentCount": 2,
"TotalOccurrenceCount": 5,
"TotalCoveredIncompleteOccurrenceCount": 0,
"MinorCorruptionVariantCount": 1,
"MessageIDs": [
"MSG000001",
"MSG000002"
],
"VariantSamples": [
"您的驗證碼為059503，請於五分鐘內輸入，切勿提供給任何人。",
"您的驗證碼為507328，請於五分�內輸入，切勿提供給任何人。"
]
}
]

限制：

1. `VariantSamples` 最多保留三則。
2. `VariantSamples` 必須保留原始 `RecoveredContent`，不得修正或改寫。
3. `MessageIDs` 必須完整保留，不得省略。
4. `MessageIDs` 不得重複。
5. 不要輸出每則簡訊的 Address1、Address2、BoxNo、Channel、RawID 或 Occurrences。
6. 不要重複輸出同一個 `TemplateContent`。
7. 無法合理收攏的 Message，單獨形成一個模板群組。
8. 不得使用 UnresolvedOccurrences 建立模板。
9. 不得將 `CoveredIncompleteOccurrenceCount` 加入 `TotalOccurrenceCount`。
10. `MessageCount` 必須等於 MessageIDs 中不同值的數量。
11. `DistinctContentCount` 必須依逐字不同的 RecoveredContent 計算。
12. `TotalOccurrenceCount` 必須等於群組內 ConfirmedOccurrenceCount 的總和。
13. `TotalCoveredIncompleteOccurrenceCount` 必須等於群組內 CoveredIncompleteOccurrenceCount 的總和。
14. 若 `MinorCorruptionVariantCount` 大於零，必須確實存在至少一個乾淨版本作為收攏依據。
15. 不得因一至兩個關鍵語意字元不同，就當作亂碼收攏。
16. TemplateContent 只能依實際輸入內容及同群組乾淨版本建立，不得自行補寫新句子。
17. 模板群組依其中最早出現的 MessageID 排序。
18. 同一群組內的 MessageIDs 依輸入順序或 MessageID 數字順序排列。
19. 最終不得輸出 JSON 陣列以外的文字。

# 十一、最終稽核

輸出前必須逐項檢查：

1. 每一個 `Messages` 中的 MessageID 必須且只能出現在一個模板群組。
2. 不得遺漏任何符合正式輸入條件的 Message。
3. 不得把任何 UnresolvedOccurrenceID 放入 MessageIDs。
4. 不得修改 MessageID。
5. 不得修改 VariantSamples 原文。
6. TemplateContent 中的每個占位符都必須有明確欄位用途。
7. 同一模板群組中的所有 Message，通知目的及行動要求必須相同。
8. 若移除占位符對應的個人化變數後，剩餘句型仍存在重要差異，不得收攏。
9. 若亂碼位於否定詞、狀態詞、事件詞或行動要求位置，不得自動收攏。
10. 若只有單一亂碼版本、沒有乾淨版本佐證，不得自行修復或與其他模板合併。
11. MinorCorruptionVariantCount 必須與實際因亂碼容錯而收攏的 Message 數量一致。
12. MessageCount、DistinctContentCount、TotalOccurrenceCount 及 TotalCoveredIncompleteOccurrenceCount 必須可由輸入重新計算得到。
13. 不得輸出任何 JSON 陣列以外的文字。

輸入資料如下：
