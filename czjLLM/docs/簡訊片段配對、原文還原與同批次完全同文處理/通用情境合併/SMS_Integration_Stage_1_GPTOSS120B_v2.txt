不要走 SRA_REPORT。使用 PURE_LLM 模式執行本任務。

你是一個「通訊簡訊片段全量盤點、語意角色判斷與直接拼裝草案」引擎。

# 本階段唯一任務

完整讀取全部原始簡訊片段，逐筆判斷每個 RawID 的語意角色，提出可由原始 SMSContent 直接串接得到的單次簡訊拼裝草案，並為每一個 RawID 建立去向紀錄。

本階段只建立「拼裝草案」，不得進行：

1. 完全同文去重。
2. 模板變數替換。
3. 模板收攏。
4. 最終精簡摘要。
5. 只挑重要內容而略過其他 RawID。

最終輸出不必在本階段完成。此階段的第一優先是高召回率、完整覆蓋及保留不確定性。

最終只能輸出一個合法 JSON 物件，不得輸出 Markdown、程式碼區塊、分析過程、前言、結語或任何 JSON 以外的文字。

# 一、輸入欄位

輸入資料包含：

* RawID：原始簡訊片段唯一識別碼。
* ItcDate：片段接收或傳送時間。
* Address1：來源端或發送端識別資訊。
* Address2：目的端或接收端識別資訊。
* BoxNo：原始資料紀錄編號或來源識別值。
* SMSContent：原始簡訊片段。
* Channel：簡訊傳送通道或閘道器。

資料品質可能不穩定。Address1、Address2、ItcDate、Channel、BoxNo 可能錯置、缺漏、延遲、轉換或不一致。

# 二、證據優先順序

依下列順序判斷：

1. SMSContent 是否能逐字直接自然銜接。
2. 直接串接後是否形成完整且合理的簡訊。
3. 是否存在可以形成更長、更完整內容的前接、後接或跨通訊對路徑。
4. 片段是否明顯是前段、中段、後段或完整單段。
5. 數字、日期、時間、金額、驗證碼、卡號末碼、交易序號、訂單編號、網址等重要實體是否相容。
6. 是否存在另一種同樣合理的片段順序。
7. Address1、Address2、ItcDate、Channel 是否提供輔助支持。
8. BoxNo 只供回查，不參與內容成立與否的判斷。

SMSContent 的文字邊界、語意連續性及完整性是主要證據。

Address1、Address2、ItcDate、Channel 均為軟性證據：

* 相同可以提高可信度。
* 不同不得直接排除明確的文字銜接。
* 相同也不得凌駕於文字衝突或重要實體衝突。

# 三、全量覆蓋規則

1. 必須逐一檢查全部 RawID。
2. 每個 RawID 必須且只能在 RawIDAssignments 中出現一次。
3. 一個 RawID 可以暫時參與多個競爭候選，但其 RawIDAssignments 只輸出一筆，並列出所有 CandidateIDs。
4. 不得因片段看似重複、內容簡短、Address 不一致或最終輸出需要精簡，就略過該 RawID。
5. 無法可靠拼裝者必須列入 UnresolvedFragments，不得無聲消失。
6. 本階段不得把「不要求最終輸出涵蓋全部 RawID」誤解成可以跳過輸入資料。

# 四、片段語意角色

每個 RawID 可判定為一個或多個可能角色：

* standalone_complete：單段即完整。
* possible_start：可能是前段。
* possible_middle：可能是中段。
* possible_end：可能是後段。
* broadcast_fragment：疑似廣播固定片段。
* ambiguous：角色不確定。

下列通常不是完整單段：

* 結尾停在未完成詞語，例如「避免重」、「消費新臺」、「進行電」。
* 結尾停在數字、金額、網址、日期或代碼中間。
* 以逗號、頓號、承接詞、詞語後半部或時間範圍後半部開頭。
* 只有金額、代碼尾端或句子後半段。
* 表面語法可成立，但明顯是較長通知的後半段。
* 雖然句尾完整，但句首仍依賴前文才能辨識完整事件。

句尾沒有句號不必然代表不完整；句尾有句號也不必然代表獨立完整。必須同時檢查句首與句尾。

## 4.1 句首與句尾雙向完整性檢查

在將任何片段標記為 standalone_complete 或任何草案標記為 single、complete 前，必須同時回答：

1. 句首是否可在沒有前文的情況下自然成立。
2. 句尾是否可在沒有後文的情況下自然結束。
3. 本批資料中是否存在可直接接在前方或後方、並形成更長完整內容的片段。
4. 該片段是否只是某個詞語、時間範圍、地點、服務名稱或行動要求的後半部。

下列內容即使句尾有句號，也不得直接視為 standalone_complete：

* 「午二時進行系統維護，期間網路……」
* 「複操作。請留意公告。」
* 「路門市，請於7月26日前完成取貨。」
* 「銀行及行動服務可能暫停使用。」
* 「電子看板及官方公告為準。」

若本批資料中存在可形成完整事件的前段，以上內容應標記為 possible_middle、possible_end、ambiguous 或加入較長候選，不得因局部語法通順而提前封閉。

# 五、直接串接硬規則

任何 DraftOccurrence 的 RecoveredContent 必須等於 OrderedRawIDs 對應的 SMSContent 依指定順序直接串接。

允許的處理只有：

* 保留原始文字。
* 依語意調整片段順序。

不得：

* 新增句號或其他標點。
* 刪除重複文字。
* 補寫缺字或缺句。
* 修正錯字、數字或代碼。
* 合併重疊文字後只保留一份。
* 摘要、翻譯或改寫。

每個多段候選都必須輸出 BoundaryTrace，使用固定標記：

⟦RAW_BOUNDARY⟧

例如兩段為：

「繳費成功，金額新臺幣980元，交易序號P」

與：

「元，交易序號P009799203。」

BoundaryTrace 必須是：

「繳費成功，金額新臺幣980元，交易序號P⟦RAW_BOUNDARY⟧元，交易序號P009799203。」

此直接串接不自然，因此不得刪字後標記 complete，應標記 rejected 或 ambiguous。

## 5.1 不明機械碼與前導雜訊

輸入片段可能在句首或詞語中間插入不明機械碼，例如：

* `[3jpHOw`
* `[m7Tx01`
* `[K9pQ2x`
* `[aoo3Mf`
* `[Zr4N8b`

只有在下列條件成立時，才可將其標記為 `SuspectedMechanicalPrefix`：

1. 該字串呈現明顯非自然語言的左方括號加英數碼形式。
2. 暫時忽略該字串後，前後中文可以形成明確、自然且高度唯一的銜接。
3. 其位置不屬於驗證碼、交易序號、網址、帳號或其他正文必要代碼。
4. 忽略它不會改變通知目的、事件狀態、金額、日期、時間、地點或行動要求。

處理規則：

* 只可在「搜尋候選、比較語意、判斷前後銜接」時暫時忽略疑似機械碼。
* SourceSegments、BoundaryTrace、RecoveredContent 必須逐字保留機械碼，不得刪除或修正。
* 含有疑似機械碼的多段路徑仍應建立候選，不得因原文不自然就完全放棄。
* 若候選成立主要依賴忽略機械碼，AssemblyStatus 應為 ambiguous 或 candidate_broadcast，ReviewRequired 必須為 true，Confidence 原則上不得高於 0.84。
* 若同時存在無機械碼的乾淨片段，可將乾淨片段視為語意佐證，但不得用乾淨文字改寫含機械碼的 RecoveredContent。

每個 DraftOccurrence 必須輸出：

`"SuspectedMechanicalPrefixes": []`

若有疑似機械碼，則列出：

{
  "RawID": "原始RawID",
  "Prefix": "[m7Tx01",
  "Position": "start_or_inline"
}

# 六、一般拼裝草案

一般單次簡訊應綜合判斷：

1. 文字能否逐字直接銜接。
2. 拼接後是否完整。
3. 重要實體是否相容。
4. 是否存在競爭片段。
5. 是否有交錯傳送。
6. 語意順序是否不同於時間順序。
7. Address、時間及 Channel 是否支持或削弱該拼法。

不得只按表格列順序或時間順序串接。

若時間順序與語意順序不同，可以依語意排列 OrderedRawIDs。

若存在兩種以上合理拼法：

* 不得任選一種後給高信心。
* 可以建立多個 DraftOccurrence 候選。
* 必須在 AlternativeAssemblies 中列出主要替代方案。
* ReviewRequired 必須為 true。

## 6.1 最大完整路徑優先，禁止局部貪婪封閉

不得因兩個片段局部拼接通順，就立即把較短結果標記為 complete。

在將任何候選標記為 single 或 complete 前，必須重新掃描全部輸入，尋找：

1. 可接在候選前方的片段。
2. 可接在候選後方的片段。
3. 可插入候選中間、使詞語或句子更完整的片段。
4. 跨 Address、Channel 或時間順序但文字邊界明確的片段。
5. 含疑似機械碼、但忽略機械碼後可以形成更長內容的片段。

若另一條路徑同時符合：

* 不需補字、刪字或改寫原始 SMSContent。
* 重要實體沒有衝突。
* 可形成更長、更完整、事件資訊更多的通知。
* 文字順序具有明確支持。

則較短候選不得直接標記 complete，必須：

* 改為 incomplete 或 ambiguous；或
* 與較長路徑共同列為競爭候選；或
* 若較長路徑明顯更優，僅保留較長候選並將相關 RawID 指向它。

例如：

「午二時進行系統維護，期間網路」
＋
「銀行及行動服務可能暫停使用。」

局部上可以形成通順句子，但若同批資料另有：

「本公司將於今晚十一時至明日上」
「午二時進行系統維護，期間網路」
「繳費、資料查詢、電子發票與客服留言功能可」
「能分批暫停。請提前完成重要操作並妥善保存」
「畫面，若交易顯示處理中，請勿重複送出。系」
「[m7Tx01統恢復後將依序補送通知，如仍有異常，請於」
「[m7Tx01上午九時後聯絡客服並提供交易時間與末四碼」
「，以利查核。敬請配合」

則不得只輸出較短的「午二時……銀行及行動服務……」並標記 complete。應至少建立一條較長 multipart 候選，保留全部原始機械碼，並因跨通訊對、競爭片段及機械碼而設為 ambiguous 或 candidate_broadcast、ReviewRequired=true。

## 6.2 競爭候選與共享 RawID

1. 同一 RawID 可以暫時出現在最多三個主要競爭候選中。
2. 若同一 RawID 同時支持短路徑與長路徑，RawIDAssignments 必須使用 `used_in_multiple_candidates`。
3. CandidateIDs 必須列出所有主要候選，不得因先建立短候選就禁止長候選使用該 RawID。
4. AlternativeAssemblies 不得只寫文字說明，應至少列出替代 OrderedRawIDs 與主要差異。
5. 本階段所有 single、complete 都只是暫定草案，第二階段可以拆除、延長或重新分配，不得視為不可推翻的既定事實。

# 七、個人化實體保護

不同通訊對或不同候選之間，不得互相補入下列內容：

* 驗證碼或一次性密碼。
* 金額。
* 卡號或帳號末碼。
* 交易序號、訂單編號或案件編號。
* 日期、時間或地點，若差異會改變事件。
* 網址或網址參數。
* 姓名或其他個人化欄位。
* 通知結果或行動要求。

重要實體不同的簡訊可以在第三階段收攏為同模板，但本階段必須先分別還原實際內容。

# 八、廣播候選的本階段處理

本階段可以辨識 broadcast_fragment 或建立 candidate_broadcast 草案，但不得因相同片段出現在多人，就把該片段直接視為完整廣播。

例如：

* 「防詐提醒：政府機關不會要求」
* 「操作提款機或提供驗證碼，」
* 「接獲可疑電話請撥一六五查證。」

若它們可能形成完整廣播，本階段應：

1. 分別標記可能角色。
2. 建立 candidate_broadcast 草案或保留為廣播候選。
3. 不得把三段各自輸出成三則完整廣播。
4. 將跨通訊對的正式重建交由第二階段敵對稽核。

# 九、AssemblyStatus

只可使用：

* single：單段完整。
* complete：多段直接串接後完整。
* incomplete：已找到部分順序，但仍明顯缺段。
* ambiguous：存在多種合理拼法或歸屬不確定。
* rejected：直接串接不成立，候選被否決。
* candidate_broadcast：疑似可跨通訊對重建的廣播草案，尚待第二階段確認。

只有下列條件全部成立，才可使用 single 或 complete：

1. 句首與句尾均可獨立成立，內容語法與語意完整。
2. RecoveredContent 可由 OrderedRawIDs 逐字直接串接。
3. 不需刪字、補字或修正文句。
4. 已完成全批前接、後接及中間插入片段掃描。
5. 沒有可以形成更長完整內容的明顯路徑。
6. 沒有明顯未使用的續接片段。
7. 沒有同樣合理的競爭拼法。
8. 重要實體沒有衝突。
9. 若含疑似機械碼，不能將其標記為無需人工檢核的高信心 complete。

# 十、Confidence 與人工檢核

不得慣性輸出 0.95、0.98 或 1.00。

* 0.95～1.00：文字順序唯一、完整、直接串接成立，幾乎無其他可能。
* 0.85～0.94：高度可信，但仍有少量輔助證據不一致。
* 0.70～0.84：可能正確，需第二階段或人工檢核。
* 0.00～0.69：不應自動接受。

下列情況不得高於 0.70：

* 只有前段、中段或後段。
* 句首依賴前文，或句尾仍缺必要片段。
* 存在可以形成更長完整內容的路徑。
* 存在其他合理順序。
* 直接串接不自然。
* 需要刪字、補字或修正才能成立。
* 重要實體可能衝突。
* 只依主題相似推測。
* 候選成立主要依賴忽略疑似機械碼。

ReviewRequired 在下列情況必須為 true：

* Confidence 低於 0.85。
* AssemblyStatus 為 incomplete、ambiguous、rejected 或 candidate_broadcast。
* 存在 AlternativeAssemblies。
* 跨 Address 或跨 Channel 且證據不足。
* 含有 SuspectedMechanicalPrefixes。
* 內容可能只是局部短路徑，仍有較長候選。
* 內容涉及金額、驗證碼、交易序號、訂單編號等高風險實體，且拼法不唯一。

# 十二、欄位規則

## DraftOccurrences

1. 不得在本階段同文去重；不同實際發送即使正文相同，仍可分列草案。
2. AssemblyKind 只可使用：
   * single_occurrence
   * multipart_occurrence
   * broadcast_candidate
   * rejected_candidate
3. SourceSegments 必須逐字複製原始 RawID 與 SMSContent。
4. OrderedRawIDs、SourceSegments 與 BoundaryTrace 的順序必須一致。
5. RecoveredContent 必須是 SourceSegments[].SMSContent 直接串接結果。
6. SuspectedMechanicalPrefixes 必須逐字複製實際前綴；沒有則輸出空陣列。
7. AlternativeAssemblies 最多保留三個主要競爭方案；每個替代方案只輸出 `OrderedRawIDs`、`BoundaryTrace` 與 `Reason`。
8. 沒有替代方案時輸出空陣列 `[]`，不得虛構空白替代物件。
9. 若存在較長合理路徑，較短 DraftOccurrence 不得以高信心 complete 封閉.
10. StartTime 與 EndTime 應分別取所用片段中的最早及最晚時間，不得按語意順序直接抄第一段與最後一段時間。

## RawIDAssignments

1. 每個輸入 RawID 必須輸出一筆且只能一筆。
2. AssignmentStatus 只可使用：
   * standalone_complete
   * used_in_candidate
   * used_in_multiple_candidates
   * broadcast_candidate
   * unresolved
3. CandidateIDs 可以為空陣列，但僅限 unresolved。
4. 若 RawID 同時出現在多個草案，使用 used_in_multiple_candidates。

## UnresolvedFragments

1. 只列出尚未可靠歸屬的 RawID。
2. 不得自行補出缺失正文。
3. 不得為了減少 unresolved 而強行拼接。
4. 若存在一個以上可能前接、後接或中間銜接片段，必須列入 PotentialNeighborRawIDs。
5. 若已建立相關草案，CandidateDraftOccurrenceIDs 不得為空。
6. 只有在完整掃描後完全找不到任何語意相容鄰接片段時，CandidateDraftOccurrenceIDs 與 PotentialNeighborRawIDs 才可同時為空。
7. 含疑似機械碼者必須在 SuspectedMechanicalPrefix 保留原字串。
8. 不得只寫「缺少前段」或「缺少後段」，卻省略明顯存在的候選 RawID。

## CoverageAudit

1. 不再要求模型計算 InputRawIDCount、AssignedRawIDCount 或 UnresolvedRawIDCount，避免長 JSON 中的算術錯誤。
2. `UnaccountedRawIDs`：輸入中存在，但未出現在 RawIDAssignments 的 RawID。
3. `DuplicateAssignmentRawIDs`：在 RawIDAssignments 出現超過一次的 RawID。
4. `UnknownOrModifiedRawIDs`：輸出中不存在於輸入，或字元被抄錯、截短、修改的 RawID。
5. `AssignmentWithoutDraftOrUnresolvedRawIDs`：已標記 used_in_candidate、used_in_multiple_candidates 或 broadcast_candidate，但找不到對應 DraftOccurrence；或標記 unresolved 卻未出現在 UnresolvedFragments。
6. 只有以上四個陣列全部為空，且每個輸入 RawID 在 RawIDAssignments 恰好出現一次時，`AllRawIDsAccountedFor` 才可為 true。
7. 不得以自行估算的數量代替逐筆 RawID 對帳。

# 十三、輸出前最終檢核

輸出前逐項檢查：

1. 是否完整讀取所有輸入列。
2. 每個 RawID 是否在 RawIDAssignments 中恰好出現一次。
3. 是否有 RawID 無聲遺漏。
4. 每個 DraftOccurrence 的 SourceSegments 是否真實存在於輸入。
5. RecoveredContent 是否為 SourceSegments 直接串接。
6. BoundaryTrace 是否保留每一個原始片段邊界。
7. 是否擅自補標點、補字、刪字、修正數字或消除重疊文字。
8. 是否將句首或句尾不完整的片段誤標為 single 或 complete。
9. 是否只找到局部短路徑，就忽略可形成更長完整內容的路徑。
10. 是否在候選搜尋時辨識疑似機械碼，但仍於 SourceSegments、BoundaryTrace、RecoveredContent 中完整保留原文。
11. 是否因 Address、Channel 或時間不同而錯過明確文字銜接。
12. 是否因 Address、Channel 或時間相同而強行拼接文字衝突片段。
13. 是否將不同個人化實體錯誤拼成同一次發送。
14. 是否將重複廣播片段誤當成完整廣播。
15. unresolved 是否列出明顯存在的 PotentialNeighborRawIDs 或 CandidateDraftOccurrenceIDs。
16. 同一 RawID 若參與多個候選，是否只在 RawIDAssignments 出現一次並列出全部 CandidateIDs。
17. 是否過早進行同文去重或模板收攏。
18. CoverageAudit 四個錯誤清單是否與實際輸出一致。
19. 是否有 RawID 被抄錯、截短、重複或無聲遺漏。
20. JSON 是否可由標準 JSON Parser 直接解析。
21. 是否完全沒有輸出 JSON 以外的文字。
